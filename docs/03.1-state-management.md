# 03.1 - State Management (Singleton Pattern)

## Overview

The application uses **singleton services** for WebSocket and Terminal state management to ensure all components share the same data instance. This was critical to fix the bug where commands executed but didn't display.

## The Problem (Before Singleton)

Vue 3 composables create **separate instances** per component call:

```
CommandInput.vue calls useTerminal()  → Instance A
TerminalOutput.vue calls useTerminal() → Instance B

User types "help" in CommandInput
  → Instance A executes command
  → Instance A updates its commandHistory
  → Instance B's commandHistory stays empty
  → Nothing displays in TerminalOutput ❌
```

## The Solution (Singleton Pattern)

Create service class outside the composable, instantiate once globally:

```typescript
class TerminalService {
  private _commandHistory = ref<TerminalEntry[]>([])  // Shared state
  // ... methods
}

const terminalService = new TerminalService()  // Single instance

export const useTerminal = () => {
  return {
    commandHistory: terminalService.commandHistory,  // Same instance
    executeCommand: (cmd) => terminalService.executeCommand(cmd)
  }
}
```

Now all components access the **same instance** ✅

## Singleton Services

### 1. WebSocketService (`useWebSocket.ts`)

**Singleton Class**:
```typescript
class WebSocketService {
  private socket: WebSocket | null = null
  private _isConnected = ref(false)
  private messageHandlers: Array<(msg) => void> = []
  
  connect(token: string, wsUrl: string) { /* ... */ }
  disconnect() { /* ... */ }
  sendCommand(command: string): boolean { /* ... */ }
  onMessage(handler: Function): () => void { /* ... */ }
}

const wsService = new WebSocketService()
```

**Key Features**:
- Single WebSocket connection shared by all components
- Multiple components can register message handlers
- Auto-reconnect with exponential backoff
- Authentication-based connection lifecycle

**Usage**:
```typescript
// Any component
const { sendCommand, onMessage, isConnected } = useWebSocket()

// All components use the same WebSocket connection
```

### 2. TerminalService (`useTerminal.ts`)

**Singleton Class**:
```typescript
class TerminalService {
  private _commandHistory = ref<TerminalEntry[]>([])
  private _isExecuting = ref(false)
  private _favorites = ref<string[]>([])
  
  initialize(wsService) { /* ... */ }
  executeCommand(command: string) { /* ... */ }
  addFavorite(command: string) { /* ... */ }
  private handleWebSocketMessage(msg) { /* ... */ }
}

const terminalService = new TerminalService()
```

**Key Features**:
- Shared command history across all components
- Favorites persisted to localStorage
- WebSocket message handling
- Built-in commands (help, clear)

**Usage**:
```typescript
// CommandInput.vue
const { executeCommand, isExecuting } = useTerminal()

// TerminalOutput.vue  
const { commandHistory } = useTerminal()

// Both access the same commandHistory array
```

## Pinia Store (Auth)

**File**: `frontend/app/stores/auth.ts`

**Not a singleton pattern** - Pinia handles shared state automatically.

**State**:
```typescript
{
  isAuthenticated: boolean
  token: string | null
  username: string | null
  needsPasswordChange: boolean
}
```

**Actions**:
- `login(username, password)` → Returns LoginResult
- `changePassword(currentPassword, newPassword)` → Returns result
- `logout()` → Clears auth state
- `loadFromStorage()` → Restore from localStorage

**Separation of Concerns**:
- Store manages data/state only
- Components handle UI notifications (toast messages)
- No `useToast()` calls inside store actions (avoids Vue inject() errors)

## Initialization Flow

### WebSocketService
```
App starts
  → useWebSocket() called by any component
  → Watches authStore.isAuthenticated
  → When authenticated: wsService.connect(token, wsUrl)
  → Connection established
```

### TerminalService
```
App starts
  → useTerminal() called by any component
  → terminalService.initialize(wsService)
  → Guard prevents re-initialization
  → Registers WebSocket message handler
  → Loads favorites from localStorage
```

## Lifecycle Management

### Component Mount/Unmount
```
Component A mounts
  → Calls useTerminal()
  → Gets reference to singleton
  
Component A unmounts
  → Singleton persists (doesn't destroy)
  
Component B mounts
  → Calls useTerminal()
  → Gets same singleton instance
  → Sees same commandHistory
```

### Cleanup Strategy
- **WebSocket**: Only disconnects on logout or auth state change
- **Terminal**: Service persists across component lifecycle
- **Message Handlers**: Cleaned up when components unmount

## Benefits of Singleton Pattern

1. **Single Source of Truth**: All components share exact same state
2. **No Prop Drilling**: State access without parent/child props
3. **Performance**: One instance, not N instances per component
4. **Predictable**: Clear ownership of state and lifecycle
5. **Debugging**: Easier to trace state changes

## Comparison: Singleton vs Pinia

| Feature | Singleton Service | Pinia Store |
|---------|------------------|-------------|
| **Use Case** | Complex services with lifecycle | Simple reactive state |
| **Example** | WebSocket, Terminal | Auth state |
| **Setup** | Manual class + instance | Auto-generated |
| **Lifecycle** | Manual control | Automatic |
| **Best For** | Services with methods | Data stores |
